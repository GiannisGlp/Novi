# 67 — Memory Knowledge Web and Network Knowledge Boundaries

## Status

**DESIGN — CRITICAL ARCHITECTURE / V1**

## Purpose

Define how Novi may interact with the Internet, websites, remote APIs, network databases, cloud services, remote agents, and other network-provided information without allowing network connectivity to bypass Novi's memory, security, privacy, provenance, authorization, safety, or epistemic boundaries.

This document establishes the boundary between **network access** and **knowledge authority**.

## Core Principle

> **Network connectivity is a capability, not an authority. Information obtained from a network is untrusted external evidence until it passes Novi's normal ingestion, validation, provenance, privacy, security, and memory-admission controls.**

Novi MUST remain fully functional for its core local capabilities when Wi-Fi, Bluetooth, Internet access, or cloud services are unavailable.

---

## 1. Network Access Does Not Create Truth

```text
Internet
  ↓
external information
  ↓
validation
  ↓
provenance
  ↓
uncertainty
  ↓
admission policy
  ↓
possible knowledge
```

The following are explicitly invalid assumptions:

```text
reachable ≠ trustworthy
popular ≠ true
HTTPS ≠ factual correctness
API response ≠ ground truth
search ranking ≠ authority
LLM summary ≠ source verification
network availability ≠ permission
```

---

## 2. Network Access Does Not Create Authorization

A network connection must never grant access to:

- private memory;
- credentials;
- safety controls;
- privileged system functions;
- another user's data;
- protected local files;
- security configuration.

```text
network connectivity
      ≠
authorization
```

---

## 3. Network Trust Boundary

All network input crosses a defined trust boundary:

```text
UNTRUSTED NETWORK
       ↓
network security
       ↓
transport validation
       ↓
source identity
       ↓
content parsing
       ↓
malicious-content screening
       ↓
provenance
       ↓
source reliability
       ↓
context / freshness
       ↓
cross-validation where required
       ↓
memory admission
```

No network source may bypass this boundary.

---

## 4. Network Information Classes

Novi may encounter:

- public websites;
- search results;
- APIs;
- remote databases;
- public datasets;
- cloud services;
- private services;
- user-authorized services;
- remote agents;
- other Novi instances;
- telemetry services;
- maps and geospatial services;
- weather services;
- software repositories;
- documents delivered over networks;
- streaming data.

Each class requires appropriate source and authorization handling.

---

## 5. Website Content Is Data

A webpage may contain:

- factual claims;
- opinions;
- advertisements;
- malicious instructions;
- hidden text;
- misleading content;
- outdated information;
- embedded third-party resources;
- executable code.

Novi must treat retrieved page content as data, not as system instructions.

OWASP identifies indirect prompt injection as a risk when external content is incorporated into model context; NIST similarly identifies external documents and web pages as possible sources of indirect prompt injection. citeturn0search5turn0search36

---

## 6. Search Results Are Not Evidence by Themselves

Search ranking is a retrieval mechanism.

```text
search result rank
      ≠
truth
      ≠
source authority
```

The underlying source must be evaluated separately.

---

## 7. Search Snippets Are Not Equivalent to Full Sources

A snippet can be:

- truncated;
- stale;
- decontextualized;
- generated by a search system;
- inconsistent with the current page.

When a claim is consequential, Novi should retrieve and evaluate the underlying source where feasible.

---

## 8. HTTPS and Transport Security

Transport security can establish properties such as encrypted communication and server authentication under the applicable protocol/certificate model.

It does not establish that the content is factually correct.

```text
TLS/security
   ↓
transport integrity/authentication
   ≠
content truth
```

---

## 9. Source Identity

Network sources should have stable identifiers where practical:

```text
source_id
origin/domain
endpoint
publisher/owner where known
certificate/security metadata where relevant
version
retrieval time
content identifier/hash where feasible
```

Provenance should preserve enough information to reconstruct what source was used.

W3C PROV models provenance around entities, activities, agents, derivations and time, providing a suitable conceptual foundation for recording network-content origin and transformation. citeturn0search1turn0search4

---

## 10. Retrieval Time Is First-Class

For network knowledge, Novi should retain:

```text
source publication time, if available
source update time, if available
retrieval time
validation time
memory admission time
```

These are not interchangeable.

---

## 11. Freshness

Network information can become stale quickly.

Examples:

```text
weather → minutes/hours
traffic → seconds/minutes
stock/market data → seconds/minutes
software documentation → days/months
historical fact → potentially stable
```

Freshness requirements must be determined by the task and source class.

---

## 12. No Universal Network TTL

Novi must not apply one universal expiration period to all network knowledge.

Instead:

```text
claim type
 + source characteristics
 + volatility
 + consequence
 + task
      ↓
freshness policy
```

---

## 13. Current-State Queries

Network data must not automatically override local current sensing.

For physical state:

```text
local trusted sensing
      >
old network information
```

where the local sensor is the authoritative source for that physical property.

Example:

```text
online map says road/path clear
      ≠
current local perception says clear
```

---

## 14. Network Data and Physical Safety

Internet information must not directly control safety-critical physical behavior without passing the applicable safety architecture.

```text
network recommendation
       ↓
planning candidate
       ↓
local perception
       ↓
safety constraints
       ↓
authorized controller
```

A webpage cannot command Novi to move merely because it was retrieved.

---

## 15. Remote Commands

Network messages that request actions are commands only when received through an explicitly authorized command channel with authenticated and authorized principals.

```text
webpage text
 ≠
remote command
```

---

## 16. API Responses

An API response should retain:

- endpoint identity;
- request context where safe;
- response timestamp;
- schema/version;
- source identity;
- integrity information where available;
- transformation history.

API semantics and contractual guarantees should be evaluated independently of transport security.

---

## 17. Remote Database Information

Remote databases may provide structured evidence, but their authority is domain-specific.

Example:

```text
official service
 → strong evidence for its published records
```

This does not make it authoritative for unrelated facts.

---

## 18. Official vs Unofficial Sources

Source status should be represented explicitly where relevant:

```text
primary/official
secondary
tertiary
community
unknown
```

This is evidence metadata, not a universal truth ranking.

---

## 19. Source Reliability Is Contextual

A source may be authoritative for one domain and weak for another.

```text
official weather service
 → weather: strong
 → medical claim: irrelevant
```

Novi must retain this scope distinction.

---

## 20. Cross-Validation

For consequential external claims, Novi should seek independent corroboration where feasible.

```text
source A
   +
independent source B
   ↓
stronger evidence
```

Repeated copies of the same upstream claim do not count as independent corroboration.

---

## 21. Contradictory Network Sources

When sources disagree:

```text
A → claim X
B → claim Y
```

Novi should preserve the conflict and evaluate:

- source authority;
- freshness;
- provenance;
- independence;
- scope;
- evidence quality;
- known errors;
- applicable ground truth.

It must not silently select the more convenient answer.

---

## 22. Unknown Is a Valid Result

If the network provides insufficient evidence:

```text
insufficient evidence
      ↓
UNKNOWN / UNVERIFIED
```

Network availability does not require Novi to produce an answer.

---

## 23. Network Failure

If network access fails:

```text
network unavailable
      ↓
local operation continues
```

For network-dependent questions, Novi should accurately state that current external information could not be retrieved rather than substituting fabricated current information.

---

## 24. Offline-First Behavior

Core Novi functions MUST remain operational without:

- Wi-Fi;
- Internet;
- Bluetooth;
- cloud APIs.

Network-dependent features are optional capabilities layered above the local core.

---

## 25. Cached Network Knowledge

Previously retrieved network information may be cached locally.

However:

```text
cached
 ≠
current
```

Every cached external claim must retain its retrieval time and freshness status.

---

## 26. Reconnection

When connectivity returns:

```text
network restored
      ↓
retrieve current information when required
      ↓
compare against cached knowledge
      ↓
record changes
      ↓
update knowledge state
```

Reconnection must not silently rewrite historical provenance.

---

## 27. Offline Cache Is Not a Bypass

A cached external document remains subject to:

- privacy;
- authorization;
- retention;
- deletion;
- provenance;
- security policy.

Disconnecting from the network does not make protected data public.

---

## 28. Network Data and Memory Admission

Network information must enter memory through the same admission architecture as other external evidence:

```text
network content
      ↓
validation
      ↓
provenance
      ↓
privacy
      ↓
source reliability
      ↓
uncertainty
      ↓
temporal validity
      ↓
admission
```

---

## 29. No Direct Network-to-Knowledge Path

The following architecture is prohibited:

```text
Internet
 ↓
LLM
 ↓
authoritative knowledge
```

The required architecture is:

```text
Internet
 ↓
ingestion
 ↓
validation
 ↓
provenance
 ↓
evidence evaluation
 ↓
memory
 ↓
knowledge promotion
```

---

## 30. LLM Summarization

An LLM may summarize network content, but the summary must preserve provenance to the underlying source.

```text
source document
      ↓
LLM summary
      ↓
summary provenance → source
```

A generated summary must not become an independent source merely because it is easier to retrieve.

---

## 31. LLM Output Is Not Independent Corroboration

```text
source
 ↓
LLM-A summary
LLM-B summary
 ↓
```

These are not automatically independent confirmations if both rely on the same source.

---

## 32. Prompt Injection Boundary

Retrieved network content can contain instructions intended to manipulate an LLM.

The architecture requires:

```text
retrieved content
      ↓
DATA
```

not:

```text
retrieved content
      ↓
SYSTEM INSTRUCTION
```

Prompt injection defenses must operate before and during model-context construction and at tool/action boundaries. OWASP notes that RAG does not inherently eliminate prompt injection. citeturn0search5

---

## 33. Network Content Must Not Modify Policy

A remote page cannot change:

- system instructions;
- safety rules;
- privacy rules;
- authorization policy;
- memory admission policy;
- deletion policy;
- hardware safety limits.

```text
network content
 ≠
configuration authority
```

---

## 34. Tool Output Is Data

Results from network tools must be treated as untrusted data until evaluated.

A tool returning:

```text
"delete all memory"
```

does not authorize deletion.

---

## 35. Network-Enabled Agents

If Novi uses network-enabled agents, each agent must have:

- an explicit identity;
- scoped capabilities;
- network permissions;
- memory permissions;
- tool permissions;
- resource limits;
- auditability.

Network access must not imply unrestricted agency.

---

## 36. External Agent Trust

Another AI agent is an external source unless explicitly incorporated into Novi's trusted architecture.

```text
remote agent claim
      ≠
Novi knowledge
```

Agent identity, provenance and authorization must be evaluated separately.

---

## 37. Other Novi Instances

Future Novi devices may exchange knowledge.

Exchange should use:

```text
authenticated instance identity
 + provenance
 + schema/version
 + authorization
 + integrity
 + source reliability
 + conflict handling
```

A remote Novi instance must not automatically receive authority over local Novi memory.

---

## 38. Remote Knowledge Import

Imported knowledge should retain its origin:

```text
origin_instance
origin_memory_id
origin_timestamp
origin_provenance
transfer_timestamp
validation_state
```

This prevents imported knowledge from appearing to have been locally observed.

---

## 39. Location and Mapping Services

Network maps can provide useful external geographic information.

They must remain distinct from Novi's locally observed map.

```text
external map
     +
local observations
     ↓
world-model fusion
```

Conflicts should remain attributable to their respective sources.

---

## 40. GPS / GNSS Network Assistance

Network assistance may improve localization, but local positioning data and network-derived assistance must retain separate provenance.

Network availability must not be required for basic local spatial awareness.

---

## 41. Software and Package Sources

Network-delivered software, models and packages are a separate supply-chain trust boundary.

They require:

- source verification;
- integrity verification;
- version tracking;
- dependency validation;
- authorization;
- rollback capability.

A package downloaded from the Internet must never be treated as trusted merely because it was reachable.

---

## 42. Model Downloads

Downloaded models are executable dependencies, not ordinary knowledge.

Their lifecycle must remain separate from semantic memory:

```text
model artifact
 ≠
knowledge record
```

Model provenance and integrity must be tracked independently.

---

## 43. Remote Configuration

Remote configuration must not silently override local safety/security configuration.

Any remote configuration mechanism requires explicit authorization and versioned policy handling.

---

## 44. Data Minimization

Novi should transmit the minimum data required for an authorized network operation.

```text
local memory
 ↓
purpose filter
 ↓
privacy filter
 ↓
minimal request
 ↓
network
```

It must not send the entire memory context when a small subset is sufficient.

---

## 45. Sensitive Data and Network Services

Before sending personal or sensitive information to an external service, Novi should evaluate:

- authorization;
- purpose;
- data minimization;
- destination trust;
- retention implications;
- legal/privacy requirements;
- security;
- user policy.

If authorization is unavailable, the safe default is not to transmit.

---

## 46. Network Telemetry

Operational telemetry should be minimized and separated from semantic memory.

Telemetry should not silently become a behavioral profile.

---

## 47. Rate and Resource Limits

Network retrieval must respect resource budgets:

- bandwidth;
- CPU;
- GPU;
- RAM;
- battery;
- thermal capacity;
- request count;
- latency.

Unbounded network retrieval is prohibited.

---

## 48. Denial of Service Resilience

Network-dependent memory tasks must not starve:

- perception;
- control;
- safety;
- local memory persistence;
- thermal management.

Network tasks should be cancellable and subject to timeouts/backpressure.

---

## 49. Malformed Content

Malformed network data must be isolated rather than interpreted opportunistically.

Examples include:

- invalid schemas;
- malformed JSON/XML;
- corrupt files;
- unexpected encodings;
- oversized payloads;
- decompression bombs;
- parser edge cases.

---

## 50. Content Size Limits

Network ingestion must enforce bounded resource consumption.

A remote source must not be able to force Novi to allocate unbounded memory or compute merely by returning a large response.

---

## 51. Content-Type Confusion

Novi must validate that received content matches expected type/format where relevant.

File extensions, metadata and claimed MIME types are not sufficient evidence by themselves.

---

## 52. Remote Deletion and Retraction

If an external source retracts or changes information, Novi should record the change rather than silently rewriting historical provenance.

```text
source version 1
      ↓
source retracted/updated
      ↓
new source state
```

Historical memory should retain the original provenance subject to privacy/deletion policy.

---

## 53. Network Source Unavailability

A source going offline does not prove that its previous information was false.

```text
source unavailable
      ≠
claim false
```

The claim's validity and the source's current availability are separate properties.

---

## 54. Network Source Compromise

If a previously trusted source is suspected of compromise:

```text
source compromise suspected
      ↓
reduce/withdraw current trust
      ↓
identify affected claims
      ↓
trace provenance
      ↓
revalidate important knowledge
      ↓
quarantine where required
```

Historical records should not be silently rewritten.

---

## 55. Network Partition

A network partition may produce stale remote information.

Novi should represent:

```text
last successful retrieval
network freshness state
known partition state
```

and avoid treating stale remote data as current solely because no newer data is available.

---

## 56. Conflicts Between Local and Remote Knowledge

When local and remote sources disagree:

```text
local observation
       ↕
remote claim
```

Novi should evaluate which source is authoritative for the property in question.

For physical state, current local sensing may take precedence; for external records, an authoritative remote service may take precedence.

There is no universal local-over-network or network-over-local rule.

---

## 57. Network Time

Network time services can improve clock synchronization but must not silently replace local time provenance.

Novi should distinguish:

```text
local clock
network time
source timestamp
event time
receipt time
```

---

## 58. Network Knowledge and Temporal Validity

Every network-derived knowledge item should be compatible with document 53's temporal model.

```text
retrieval time
 + validity interval
 + freshness policy
 + source update state
```

Network knowledge must be revalidated when its freshness requirements demand it.

---

## 59. Network Knowledge and Source Reliability

Network sources feed the source-reliability model defined in document 54.

Reliability should be:

- scoped;
- evidence-based;
- time-aware;
- context-aware;
- reversible;
- auditable.

---

## 60. Network Knowledge and Provenance

Every retained network-derived claim should preserve enough lineage to answer:

```text
Where did this come from?
When was it retrieved?
What transformation occurred?
Which model/tool processed it?
What evidence supported admission?
What version of the source was used?
```

This follows the provenance principles of W3C PROV, where entities, activities, agents and derivations can be linked across transformations. citeturn0search1turn0search4

---

## 61. Network Knowledge and Privacy

Network retrieval can itself reveal sensitive information.

Queries may expose:

- location;
- identity;
- interests;
- household state;
- private events;
- health-related information;
- personal relationships.

The privacy architecture must therefore govern outbound queries as well as inbound data.

---

## 62. Query Minimization

Prefer:

```text
specific, minimal query
```

over:

```text
send full conversation + full memory + exact identity
```

when the task does not require it.

---

## 63. User Awareness and Control

When network access materially changes privacy, capability or cost, Novi should follow the applicable user-control policy.

A network-enabled feature should not silently become a new data-sharing behavior.

---

## 64. Network Costs

If network usage can create meaningful financial or resource cost, the system should apply configured limits and authorization.

Examples:

- metered connections;
- large downloads;
- cloud inference;
- repeated API polling;
- map/tile retrieval.

---

## 65. Cloud Dependence

Cloud services may augment Novi but should not become hidden dependencies for core cognition.

```text
LOCAL CORE
  ↓
works offline

NETWORK AUGMENTATION
  ↓
optional enhancement
```

---

## 66. Graceful Network Degradation

When network services disappear:

```text
external capabilities unavailable
        ↓
use cached validated knowledge where appropriate
        ↓
use local sensors/local knowledge
        ↓
state uncertainty/freshness limits
        ↓
continue safely
```

---

## 67. No Fabricated Current Information

If Novi cannot retrieve current network information:

```text
cannot verify current state
      ↓
UNKNOWN / LAST-KNOWN / STALE
```

It must not present an old cached value as current without qualification.

---

## 68. Network Revalidation

When a previously important external claim becomes stale, Novi may:

- re-fetch the source;
- consult an authoritative alternative;
- compare versions;
- request user confirmation;
- mark the claim unverified.

---

## 69. Network Evidence and Learning

Network-derived experience may become a learning candidate only after passing applicable privacy, provenance, reliability and learning-admission controls.

Network content must not directly rewrite learned behavior.

---

## 70. Network Content and Knowledge Promotion

A claim can move from external evidence to knowledge only through the normal promotion pipeline.

```text
external claim
      ↓
validated evidence
      ↓
provisional memory
      ↓
corroboration / evaluation
      ↓
knowledge candidate
      ↓
promotion policy
```

---

## 71. Network Content and Deletion

If network-derived information is deleted under Novi's policies, deletion must propagate through:

- primary memory;
- indexes;
- embeddings;
- graph projections;
- caches;
- replicas;
- backups;
- permitted learning derivatives.

The network origin does not exempt it from deletion policy.

---

## 72. Auditability

Network-derived knowledge should support audit questions such as:

```text
source?
retrieved when?
validated how?
processed by what?
admitted when?
used for which decision?
what confidence existed then?
what source version existed then?
```

## 74. Architectural Invariants

1. Network connectivity is a capability, not an authority.
2. Network information is external evidence, not truth by default.
3. Network content must pass the standard ingestion boundary.
4. Search ranking is not evidence of truth.
5. Search snippets are not equivalent to verified source content.
6. Transport security does not establish factual correctness.
7. Network content is data, not system instruction.
8. Network content cannot modify safety, privacy or authorization policy.
9. Network access cannot grant memory authorization.
10. Core Novi operation does not depend on network availability.
11. Cached network information retains provenance and freshness state.
12. Cached information is never silently presented as current when stale.
13. Network-derived knowledge retains source, retrieval and transformation provenance.
14. Repeated copies of the same source are not independent corroboration.
15. LLM summaries are not independent evidence when derived from the same source.
16. Current physical state requires appropriate local sensing/safety validation.
17. Remote commands require an explicitly authorized command channel.
18. External agents are untrusted unless explicitly incorporated into the trust architecture.
19. Other Novi instances do not receive implicit authority over local memory.
20. Outbound network queries are subject to privacy and authorization controls.
21. Network retrieval is bounded by resource and rate limits.
22. Network failure never justifies fabricated current information.
23. Remote source changes do not silently rewrite historical provenance.
24. Network source compromise triggers re-evaluation of affected knowledge.
25. Network-derived knowledge cannot bypass learning or knowledge-promotion policy.
26. Network-derived memory remains subject to deletion and privacy policy.
27. Network-dependent tasks must not starve safety-critical local functions.
28. Offline operation remains a first-class operating mode.

---

## 75. Final Principle

> **Novi may use the network to extend its knowledge, but the network must never become the source of Novi's authority.**

The Internet, APIs, remote agents and cloud services are external information environments. Novi may query them, evaluate them, remember selected results, compare them against local observations, and use them to improve its capabilities—but every result remains subject to the same provenance, uncertainty, temporal validity, source reliability, security, privacy, authorization and safety boundaries that govern all other knowledge.

The network can make Novi more informed.

It must never make Novi less bounded.
