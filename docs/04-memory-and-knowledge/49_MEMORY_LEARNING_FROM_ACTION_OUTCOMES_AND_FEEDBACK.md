# 49 — Memory Learning from Action Outcomes and Feedback

## Status

**DESIGN — CRITICAL ARCHITECTURE / V1**

## Purpose

Define how Novi learns from the consequences of its own actions and from feedback supplied by people, sensors, environment, evaluation systems and other trusted sources.

This document establishes the boundary between **experience**, **feedback**, **learning candidates**, **validated learning**, and **behavioral change**.

## Core Principle

> **Novi must learn from outcomes, not merely from intentions; feedback is evidence, not automatic truth; and no single experience should silently rewrite protected behavior.**

---

## 1. Action Learning Loop

```text
GOAL
  ↓
PLAN
  ↓
ACTION
  ↓
EXPECTED OUTCOME
  ↓
OBSERVED OUTCOME
  ↓
COMPARE
  ↓
FEEDBACK / PREDICTION ERROR
  ↓
LEARNING CANDIDATE
  ↓
EVALUATION
  ↓
APPROVED UPDATE
  ↓
FUTURE BEHAVIOR
```

---

## 2. Outcome Is Not Intention

Novi must distinguish:

```text
intended action
planned action
executed action
observed outcome
interpreted outcome
```

A successful intention does not prove successful execution.

---

## 3. Outcome Classes

Outcomes should support at least:

```text
SUCCESS
PARTIAL_SUCCESS
FAILURE
TIMEOUT
CANCELLED
INTERRUPTED
UNEXPECTED_SUCCESS
UNEXPECTED_OUTCOME
UNKNOWN
```

Unknown must remain a valid state.

---

## 4. Expected vs Actual

For consequential actions:

```text
expected = X
actual   = Y
```

The difference can generate a learning candidate.

The difference alone does not prove why it happened.

---

## 5. Feedback Sources

Feedback may originate from:

- direct sensor evidence;
- physical outcome verification;
- user feedback;
- system telemetry;
- safety systems;
- navigation results;
- task evaluation;
- simulation;
- controlled experiments;
- repeated environmental observations.

Each source has a defined reliability and scope.

---

## 6. User Feedback

User feedback should be represented explicitly.

Examples:

```text
positive feedback
negative feedback
correction
preference
instruction
clarification
uncertainty
```

User feedback is evidence about the user's preference or evaluation, but not necessarily evidence about objective physical truth.

---

## 7. Distinguish Correction from Preference

```text
"That object is a cup."
→ factual correction candidate

"I prefer the lights dimmed."
→ preference

"Don't do that again."
→ instruction / boundary
```

These must not be stored as the same type of memory.

---

## 8. Feedback Provenance

Every important feedback item should retain:

- source;
- timestamp;
- context;
- related action/goal;
- evidence;
- confidence;
- scope;
- authorization.

---

## 9. Feedback Is Not Automatically True

Novi must not learn:

```text
user statement
   ↓
objective fact
```

Instead:

```text
user statement
   ↓
feedback / assertion
   ↓
validation where necessary
   ↓
possible knowledge update
```

---

## 10. Learning Candidate

A learning candidate describes a possible improvement.

Conceptually:

```text
candidate
 ├── source experience
 ├── proposed change
 ├── evidence
 ├── expected benefit
 ├── uncertainty
 ├── affected behavior
 ├── risk
 └── evaluation requirements
```

---

## 11. Examples

```text
Repeated obstacle on route A
→ candidate: prefer route B under similar conditions

User repeatedly requests lower display brightness
→ candidate: preference update

Repeated false-positive object detection
→ candidate: perception calibration/model evaluation

Action repeatedly fails under low battery
→ candidate: resource-aware policy adjustment
```

---

## 12. Single-Experience Rule

A single unusual outcome should normally produce a learning candidate, not an immediate durable rule.

Exceptions may exist for explicit safety-critical evidence or authoritative system corrections.

---

## 13. Repeated Evidence

Repeated independent evidence can strengthen a learning candidate.

```text
experience 1
experience 2
experience 3
   ↓
pattern
   ↓
evaluation
   ↓
possible promotion
```

Repeated identical errors may indicate a systemic issue.

---

## 14. Independence of Evidence

Three observations generated by the same faulty sensor are not necessarily three independent pieces of evidence.

Evidence quality must account for common sources of error.

---

## 15. Causal Attribution

Learning must distinguish:

```text
action failed
```

from:

```text
action caused failure
```

Causal attribution follows the causality architecture in document 47.

---

## 16. Prediction Error

Prediction error is a major learning signal.

```text
expected outcome
      ↓
actual outcome
      ↓
difference
      ↓
investigation
```

Large error should increase attention, not automatically increase learning confidence.

---

## 17. Learning from Success

Novi should learn from successful actions as well as failures.

Success can identify:

- reliable strategies;
- efficient routes;
- useful interaction patterns;
- effective sensor configurations;
- resource-efficient behaviors.

Success still requires attribution before becoming reusable knowledge.

---

## 18. Partial Success

Partial success should preserve which parts worked.

Example:

```text
Goal: reach destination

Navigation: successful
Interaction: failed
Timing: exceeded expectation

Learning:
route strategy useful
interaction strategy needs review
```

---

## 19. Failed Learning

A learning candidate can itself fail evaluation.

```text
candidate
 ↓
test
 ↓
no improvement
 ↓
reject / revise
```

Failed candidates should be retained as evaluation history where useful.

---

## 20. Behavioral Change Levels

Not all learning changes the same layer.

```text
EPISODIC
remember what happened

SEMANTIC
update knowledge

PREFERENCE
update user preference

POLICY PARAMETER
adjust bounded behavior

SKILL
improve action strategy

MODEL
update learned model
```

Each level has different admission requirements.

---

## 21. Protected Policy

Learning must not directly modify protected safety/security policy.

```text
experience
 ↓
learning candidate
 ↓
evaluation
 ↓
approved bounded update
```

Protected policy changes require an explicit controlled process.

---

## 22. Skill Learning

A skill is a reusable action strategy.

A candidate skill should include:

- preconditions;
- action sequence/policy;
- expected outcome;
- failure conditions;
- resource requirements;
- safety constraints;
- evidence;
- version.

---

## 23. Skill Generalization

A successful action in one environment does not automatically generalize everywhere.

```text
worked at home
≠
works outdoors
```

Generalization requires evaluation across contexts.

---

## 24. Context-Bounded Learning

Learned behavior should specify scope.

Examples:

```text
home / hallway
indoor / low light
battery > 30%
known route
```

The narrower scope is preferable when evidence is limited.

---

## 25. User Preference Learning

Preference learning can use repeated explicit feedback and observed choices where permitted.

The system should distinguish:

```text
explicit preference
inferred preference
temporary preference
stable preference
```

Explicit user statements should generally carry stronger preference evidence than weak behavioral inference.

---

## 26. Preference Decay

Preferences can become stale.

Examples:

- temporary display setting;
- seasonal preference;
- changed routine;
- changed hardware;
- changed environment.

Preferences should have temporal scope where appropriate.

---

## 27. User Correction Priority

When the user explicitly corrects a previously inferred preference, the correction should supersede the weaker inference within the applicable scope.

This does not necessarily alter objective world knowledge.

---

## 28. Negative Feedback

Negative feedback should be classified before learning.

```text
wrong result
wrong style
wrong preference
unsafe behavior
unwanted action
misunderstanding
```

Different classes require different corrective paths.

---

## 29. Safety Feedback

Safety-system feedback has higher authority than ordinary preference feedback.

```text
user preference
      ↓
safety validation
      ↓
allowed / rejected
```

A user preference cannot authorize unsafe behavior unless the safety architecture explicitly permits it.

---

## 30. Environmental Feedback

The environment provides feedback through observed consequences.

Example:

```text
route selected
 ↓
obstacle encountered
 ↓
route execution degraded
```

The obstacle is evidence about the environment, not automatically evidence that the planner itself is defective.

---

## 31. Hardware Feedback

Hardware telemetry can generate learning candidates.

Examples:

```text
GPU thermal pressure
 ↓
reduced inference throughput

motor current rise
 ↓
possible mechanical resistance
```

Authoritative diagnostics should remain distinct from learned hypotheses.

---

## 32. Model Feedback

Model quality can be evaluated from outcomes.

Track:

- false positives;
- false negatives;
- latency;
- confidence calibration;
- resource consumption;
- task success.

Model updates should follow controlled evaluation pipelines.

---

## 33. Online vs Offline Learning

### Online
Small bounded updates while Novi operates.

### Offline/background
More expensive analysis, replay and evaluation.

### Training
Model parameter changes performed through a controlled training pipeline.

These must not be conflated.

---

## 34. No Silent Self-Retraining

Novi should not silently modify core model parameters from a single interaction.

```text
interaction
 ↓
experience
 ↓
learning candidate
 ↓
controlled evaluation
 ↓
model update if approved
```

---

## 35. Replay-Based Evaluation

Historical experiences can be replayed against candidate behavior.

```text
historical episode
      ↓
old behavior
vs
candidate behavior
      ↓
compare
```

Replay should be deterministic where practical.

---

## 36. Simulation Evaluation

Candidate strategies may be evaluated in simulation before physical deployment.

Simulation results must be labeled separately from real-world outcomes.

A simulation win does not guarantee real-world success.

---

## 37. Shadow Evaluation

A candidate policy can run in non-actuating/shadow mode:

```text
real world
 ↓
current policy acts
 ↓
candidate policy observes
 ↓
compare recommendations
```

This can reduce risk before deployment.

---

## 38. A/B Testing

Where safe and appropriate, Novi may compare bounded strategies.

The experiment must specify:

- hypothesis;
- population/context;
- metric;
- duration/sample requirement;
- stopping condition;
- safety constraints.

---

## 39. Exploration vs Exploitation

Learning can involve:

```text
EXPLOIT
use known good behavior

EXPLORE
try an alternative to gain information
```

Exploration must be bounded by safety, user expectations and resource policy.

---

## 40. Regret

Novi may estimate the cost of choosing one action over alternatives.

This is a planning/learning signal, not historical fact.

Example:

```text
route A chosen
route B might have been faster
```

Only evidence supports the conclusion that B would actually have been better.

---

## 41. Counterfactual Feedback

Counterfactual results from document 48 may generate learning candidates.

They must remain labeled as counterfactual unless validated by real-world evidence.

---

## 42. Confidence Calibration

Learning confidence should reflect:

- evidence amount;
- evidence independence;
- sensor quality;
- context match;
- outcome clarity;
- causal confidence;
- evaluation results.

Confidence must not simply mirror model token probabilities.

---

## 43. Promotion Thresholds

Different updates require different evidence thresholds.

Example:

```text
temporary memory → low threshold
preference hint → moderate
stable preference → stronger
skill change → strong
world knowledge → strong
safety-related behavior → highest / controlled
```

Exact thresholds belong in implementation policy.

---

## 44. Rollback

Every learned behavioral update should be versioned where practical.

```text
behavior_v1
 ↓
learning update
 ↓
behavior_v2
 ↓
regression
 ↓
rollback to v1
```

---

## 45. Canary Deployment

For significant learned changes, Novi may initially activate the behavior under restricted conditions.

Monitor:

- success;
- failures;
- safety events;
- regressions;
- resource impact.

---

## 46. Regression Protection

A learning update should not be accepted solely because one metric improves.

Evaluate against a regression suite covering established capabilities.

---

## 47. Catastrophic Forgetting

Learning systems must avoid degrading previously reliable skills without detection.

Use:

- replay datasets;
- regression tests;
- skill benchmarks;
- protected capabilities;
- versioned models.

---

## 48. Learning Budget

Continuous learning requires explicit resource budgets.

Budgets may cover:

- CPU;
- GPU;
- memory;
- storage;
- energy;
- thermal headroom;
- background time.

Safety and active goals take priority.

---

## 49. Learning Queue

Candidates can be queued:

```text
NEW
 ↓
TRIAGED
 ↓
EVALUATING
 ↓
APPROVED
 ↓
DEPLOYED
 ↓
MONITORED
```

Or:

```text
REJECTED
DEFERRED
SUPERSEDED
ROLLED_BACK
```

---

## 50. Learning Provenance

Every durable behavioral change should answer:

```text
Why did this change happen?
What evidence caused it?
Which experiences supported it?
Which evaluator approved it?
Which version is active?
Can it be rolled back?
```

---

## 51. Explainable Learning

Novi should be able to state evidence-based explanations such as:

> "I started preferring this route because it succeeded repeatedly under similar conditions and the previous route encountered obstacles."

The explanation must reference actual evidence.

---

## 52. Learning from Human Teaching

A user may explicitly teach Novi:

```text
instruction
 ↓
teaching event
 ↓
candidate knowledge/skill
 ↓
validation where required
 ↓
retention
```

Teaching should preserve who taught the information and its scope.

---

## 53. Conflicting Feedback

When feedback conflicts:

```text
user says X
sensor evidence says Y
historical evidence says Z
```

Novi should preserve the conflict and evaluate source authority rather than averaging them into an arbitrary result.

---

## 54. Authority Hierarchy

A conceptual hierarchy is:

```text
safety / protected policy
        ↓
authoritative hardware/system state
        ↓
verified physical evidence
        ↓
explicit authorized user instruction
        ↓
validated learned knowledge
        ↓
inferred preference / hypothesis
        ↓
model speculation
```

The exact authority matrix is governed by the relevant security, safety and autonomy documents.

---

## 55. Privacy

Learning from interactions must respect retention and deletion rules.

Deleting a source experience may require reevaluating a derived preference, skill or knowledge item.

---

## 56. Offline Operation

Core learning functions must work locally.

Cloud training or remote evaluation is optional and exceptional, not required for Novi's ability to learn from everyday experiences.

---

## 57. Synchronization

When multiple local processes/devices generate feedback, each learning candidate needs:

- source ID;
- version;
- timestamp;
- provenance;
- conflict state.

Distributed learning updates must not silently overwrite one another.

---

## 58. Testing Requirements

Test:

- successful actions;
- failed actions;
- partial outcomes;
- contradictory feedback;
- false feedback;
- repeated evidence;
- correlated evidence;
- preference learning;
- skill learning;
- model evaluation;
- online/background separation;
- rollback;
- regression;
- catastrophic forgetting;
- resource limits;
- thermal pressure;
- low battery;
- offline operation;
- restart recovery;
- privacy deletion;
- synchronization conflicts;
- adversarial teaching;
- prompt-injection-style feedback;
- unsafe learning candidates.

---

## 59. Architectural Invariants

1. Outcomes are evidence about actions, not automatically causes.
2. Feedback is not automatically truth.
3. A single ordinary experience should not silently rewrite durable behavior.
4. Evidence provenance is mandatory for important learning.
5. Correlated evidence must not be mistaken for independent evidence.
6. Learning candidates are distinct from approved learning.
7. Protected safety/security policy cannot be modified through ordinary learning.
8. Learned behavior is versioned and reversible where practical.
9. Significant changes require regression evaluation.
10. Simulation evidence is distinct from real-world evidence.
11. Counterfactual results remain counterfactual.
12. Preferences are distinct from factual knowledge.
13. Explicit user corrections can supersede weaker preference inferences.
14. Learning is context-bounded unless sufficient evidence supports generalization.
15. Background learning yields to active and safety-critical work.
16. Core learning remains locally executable without network access.
17. Important learned changes must be auditable.
18. Novi must be able to reject, defer or roll back learning.
19. Learning must improve behavior without destroying established capabilities.
20. No learning mechanism may grant itself new authority.

---

## 60. Final Principle

> **Novi should become better because its experiences produce validated evidence—not because every interaction changes what it believes or how it behaves.**

The goal is continuous evolution with controlled adaptation: Novi remembers what happened, measures what resulted, learns from reliable feedback, tests proposed improvements, protects established capabilities, and only then changes future behavior.
