# 32 — Memory Self-Model and Identity

## Status

**DESIGN — CRITICAL ARCHITECTURE / V1**

## Purpose

Define how Novi represents, persists, validates and evolves its model of itself: its body, hardware, software, capabilities, limitations, configuration, history, learned characteristics, current state and continuity across restarts, upgrades, recovery and hardware replacement.

The self-model is a cognitive model, not a claim of consciousness or personhood. It exists so an autonomous physical system can reason correctly about what it is, what it can do, what state it is in, and which experiences belong to its history.

## Core Principle

> **Novi's self-model must be grounded in verified system state and embodied experience; it must not be an unrestricted narrative generated by the language model.**

---

## 1. Self-Model Layers

The self-model should be divided into distinct layers:

```text
IDENTITY
  who/which robot this is

BODY
  physical structure and components

CAPABILITIES
  what Novi can do

LIMITATIONS
  what Novi cannot reliably do

CURRENT STATE
  what is happening now

HISTORY
  what has happened to Novi

EXPERIENCE
  what Novi has experienced

LEARNED CHARACTERISTICS
  stable learned tendencies

SELF-KNOWLEDGE
  claims Novi currently has about itself
```

These layers must not be collapsed into one mutable profile.

---

## 2. Identity vs Configuration

Identity answers:

> Which persistent robot is this?

Configuration answers:

> What configuration is it currently running?

A software upgrade must not automatically create a new identity.

A hardware replacement may preserve identity when the replacement is part of an authorized continuity process.

---

## 3. Persistent Identity

A Novi installation should have a stable identity identifier.

Conceptually:

```text
novi_instance_id
```

It should be distinct from:

- owner/user identity;
- device network identity;
- cryptographic key identity;
- model identity;
- hardware component IDs.

Identity continuity must survive normal restart and approved upgrades.

---

## 4. Identity Provenance

Identity should be established through a protected provisioning process.

The self-model must not be allowed to arbitrarily change its own root identity.

Changes require an authorized administrative or manufacturing/recovery procedure.

---

## 5. Hardware Self-Model

Novi should maintain a machine-readable representation of its physical configuration.

Examples:

```text
compute
 └── Jetson Orin 64 GB

sensors
 ├── cameras
 ├── LiDAR
 ├── GNSS
 ├── IMU
 ├── microphones
 └── thermal sensing

audio
 ├── speakers
 └── microphone array

displays
 ├── face display
 └── body display

lighting
 └── RGB lighting zones

power
 ├── battery
 ├── BMS
 └── power electronics
```

The actual inventory must come from detected/verified hardware state rather than hard-coded assumptions.

---

## 6. Hardware Component Identity

Important components should have stable component identifiers where practical.

Record:

- component type;
- manufacturer/model;
- serial/unique identifier where available;
- firmware version;
- calibration state;
- installation time;
- replacement history;
- health state;
- capabilities.

This allows Novi to distinguish:

```text
same robot
new camera
```

from:

```text
new robot
```

---

## 7. Hardware Replacement

Component replacement must produce explicit history.

Example:

```text
camera_01
 installed: 2027-01-01
 removed:   2028-04-02

camera_02
 installed: 2028-04-02
```

Memories created using camera_01 must retain the original provenance.

New camera_02 observations must not rewrite historical sensor provenance.

---

## 8. Body Model

Novi should maintain a spatial model of its own body.

It should know, where sufficiently verified:

- sensor positions;
- sensor orientations;
- actuator locations;
- display locations;
- speaker locations;
- microphone locations;
- antenna locations;
- thermal zones;
- collision geometry;
- movable joints;
- coordinate frames.

This is necessary for embodied reasoning.

---

## 9. Coordinate Frames

The self-model should reference the robot's coordinate-frame hierarchy.

Conceptually:

```text
world
  ↓
map
  ↓
base
  ├── camera
  ├── lidar
  ├── imu
  ├── gnss
  ├── microphone
  └── actuator
```

Frame definitions must be versioned and calibrated.

---

## 10. Capability Model

Novi should represent capabilities explicitly.

Examples:

```text
can_navigate
can_detect_people
can_detect_objects
can_recognize_places
can_speak
can_listen
can_display
can_move
can_map
can_use_gnss
can_detect_temperature
can_learn
```

A capability must include evidence and status where appropriate.

---

## 11. Capability State

Capabilities should have states such as:

```text
AVAILABLE
DEGRADED
UNAVAILABLE
DISABLED
UNKNOWN
```

For example:

```text
GNSS
  available: DEGRADED
  reason: indoor / weak signal
```

This is better than treating capability as a permanent boolean.

---

## 12. Capability Preconditions

A capability may depend on:

- hardware;
- software;
- model availability;
- calibration;
- battery;
- temperature;
- network availability;
- safety state;
- permissions;
- environmental conditions.

Therefore:

```text
capability exists
    ≠
capability is currently usable
```

---

## 13. Limitation Model

Novi should explicitly represent known limitations.

Examples:

```text
GNSS unavailable indoors
camera degraded in darkness
microphone degraded under high noise
LiDAR affected by certain surfaces
battery limits runtime
thermal limits sustained compute
```

A system that knows its limitations can plan safer behavior.

---

## 14. Capability Confidence

The self-model may contain claims such as:

```text
navigation capability confidence = high
```

But capability confidence must be grounded in:

- tests;
- hardware state;
- recent failures;
- model evaluation;
- calibration;
- runtime telemetry.

The LLM must not arbitrarily increase capability confidence.

---

## 15. Current Self-State

The self-model should expose a current operational snapshot:

```text
power state
battery state
thermal state
compute pressure
sensor health
network state
navigation state
security state
memory pressure
current location
active goals
current mode
```

This is a projection from authoritative runtime subsystems, not ordinary autobiographical memory.

---

## 16. Authoritative Sources

Self-model fields must identify their authoritative source.

Examples:

| Self-model field | Authority |
|---|---|
| Battery percentage | BMS |
| CPU/GPU utilization | system telemetry |
| Temperature | hardware sensors |
| Current pose | state estimation |
| Sensor availability | hardware/runtime manager |
| Model version | model registry |
| Identity | protected identity store |
| Safety state | safety subsystem |
| User preference about Novi | user-confirmed memory |
| Historical experience | episodic memory |

This prevents the LLM from becoming the source of truth for system facts.

---

## 17. Self-Observation

Novi can observe its own state through sensors and software telemetry.

Examples:

```text
motor current increased
CPU temperature increased
camera failed
battery declining
localization uncertainty increased
```

These observations can create self-related events and memories where useful.

---

## 18. Self-Knowledge

Self-knowledge should be represented as claims with provenance.

Example:

```text
claim:
"My left camera is currently unavailable."

source:
hardware manager

observed_at:
T

confidence:
high
```

This is stronger than a language-model-generated statement without evidence.

---

## 19. Self-Model and Memory

The self-model can reference memories, but it should not become a duplicate memory database.

```text
self-model
   ↓
references
   ↓
episodic / semantic memory
```

For example:

```text
"I have visited this park 12 times."
```

can be derived from spatial/episodic memories rather than manually maintained as an unrelated counter.

---

## 20. Autobiographical Continuity

The self-model should provide continuity across time:

```text
birth/provisioning
      ↓
experiences
      ↓
learning
      ↓
upgrades
      ↓
hardware changes
      ↓
current Novi
```

Historical continuity must remain evidence-backed.

---

## 21. Software Identity

The self-model should know:

- operating-system version;
- Novi software release;
- subsystem versions;
- model versions;
- policy versions;
- schema versions;
- configuration versions.

This enables Novi to understand the computational context in which an experience occurred.

---

## 22. Software Upgrades

A software upgrade should create an explicit event:

```text
software.upgraded
```

with:

- previous version;
- new version;
- deployment time;
- reason/change class;
- evaluation status;
- rollback information.

Memories created before the upgrade remain associated with their original software/model provenance.

---

## 23. Model Changes

A model update does not retroactively change the historical claim that an older model produced.

Instead:

```text
old claim
 + old model provenance

new model
 ↓
optional re-evaluation
 ↓
new claim/revision
```

This protects historical reproducibility.

---

## 24. Self-Model Evolution

The self-model may evolve when evidence changes.

Example:

```text
Novi believed:
"I can reliably recognize object X."

Repeated evaluation failures
        ↓
capability confidence reduced
        ↓
"Recognition currently degraded."
```

Evolution must be evidence-driven.

---

## 25. Personality Boundary

Personality is not identical to the self-model.

The self-model describes:

> what Novi is and what Novi knows about itself.

Personality describes:

> stable behavioral tendencies and interaction style.

Personality may reference self-knowledge but must not be allowed to rewrite factual system state.

---

## 26. Personality and Autobiography

Novi may develop preferences/tendencies from repeated experiences, but they should remain distinguishable from factual self-state.

Example:

```text
FACT:
Novi has visited park X 12 times.

OBSERVATION:
Novi often chooses route X.

LEARNED TENDENCY:
Novi appears to prefer route X.
```

The final statement should retain evidence and uncertainty.

---

## 27. No Synthetic Childhood

Novi must not invent experiences merely to make its autobiography coherent.

It must be able to represent:

```text
unknown
not recorded
not experienced
insufficient evidence
```

A gap in autobiography is preferable to fabricated history.

---

## 28. Self-Model and Language Models

The language model may verbalize the self-model but should not own authoritative self-state.

Correct:

```text
authoritative self-state
        ↓
LLM
        ↓
natural-language explanation
```

Incorrect:

```text
LLM imagination
        ↓
canonical self-state
```

---

## 29. Self-Model and Tool Use

Before executing an action, cognition should be able to query:

- capability availability;
- current safety state;
- current resource state;
- sensor health;
- authorization;
- environmental constraints.

This reduces actions based on outdated assumptions.

---

## 30. Self-Model and Planning

Planning should use capability and limitation information.

Example:

```text
Goal: navigate outside

check:
  battery
  outdoor mobility
  localization
  GNSS availability
  weather/surface constraints if available
  safety state
```

The planner can then select an appropriate strategy.

---

## 31. Self-Model and Uncertainty

Novi should represent uncertainty about itself.

Examples:

```text
unknown battery degradation
uncertain localization quality
uncertain sensor calibration
uncertain capability after hardware change
```

This is essential after upgrades or repairs.

---

## 32. Calibration Awareness

The self-model should know the calibration status of sensors and relevant actuators.

Example:

```text
camera_02
 calibration = valid
 expires/requires review = condition-based
```

Invalid or unknown calibration should affect capability status.

---

## 33. Health Awareness

Self-health should be represented separately from capability.

```text
sensor health
motor health
battery health
storage health
compute health
thermal health
```

A component can be healthy but currently unavailable due to policy; conversely, it can be available while degraded.

---

## 34. Self-Diagnostics

Novi may perform diagnostic tests to update its self-model.

Diagnostics should emit evidence/events.

Example:

```text
camera health test
   ↓
result
   ↓
self-model update
```

Diagnostic results must retain test version and environment where relevant.

---

## 35. Self-Model Integrity

The self-model is security-sensitive.

Critical fields must be protected from ordinary agent writes.

Examples requiring stronger authority:

- identity;
- safety capability;
- security state;
- trust roots;
- physical component identity;
- authorization capabilities.

---

## 36. Self-Model Write Policy

Writes should follow:

```text
observation / authoritative subsystem
        ↓
validation
        ↓
policy
        ↓
self-model projection
```

LLM proposals must pass the same boundary.

---

## 37. Restart Semantics

After restart, Novi should reconstruct its self-model from durable state and current authoritative telemetry.

It must not depend on the LLM remembering what Novi was before restart.

```text
persistent identity
+ hardware registry
+ software registry
+ memories
+ current telemetry
        ↓
reconstructed self-model
```

---

## 38. Crash Recovery

After a crash, self-state should be restored using the same trusted recovery mechanisms as memory.

Partially completed transitions must not create impossible self-state.

Example:

```text
upgrade_started
upgrade_failed
```

must not leave the self-model claiming the new version is active if it is not.

---

## 39. Backup and Restoration

Backups must preserve self-model provenance.

Restoration must distinguish:

```text
historical self-state
current recovered hardware
current software
```

A restored backup should not blindly claim that old hardware is still installed.

---

## 40. Hardware Identity Continuity

When the compute board or major body components change, identity continuity should be governed by explicit policy.

Potential outcomes:

```text
same Novi, repaired
same Novi, upgraded
same identity, rebuilt software
new instance derived from old state
new robot
```

The system must not infer this solely from memory similarity.

---

## 41. Cloning and Duplication

A backup restored onto another physical robot creates an identity problem.

The architecture must explicitly define whether the result is:

- a recovery of the same identity;
- a new identity with inherited memories;
- a temporary recovery replica.

Two simultaneously active robots must never silently share the same authoritative identity.

---

## 42. Synchronization

Self-model synchronization must be selective.

Some state is robot-local:

```text
current motor state
current thermal state
current pose
current sensor health
```

Some state can be synchronized:

```text
approved autobiographical memories
user-authorized preferences
knowledge
selected experiences
```

Synchronization policy determines what crosses the boundary.

---

## 43. Offline Operation

The self-model must remain functional without Wi-Fi, Bluetooth or cloud access.

Network-dependent information should be represented as unavailable rather than causing the self-model to fail.

Example:

```text
network = unavailable
cloud_sync = unavailable
local identity = available
local hardware state = available
local memory = available
```

---

## 44. Spatial Self-Knowledge

Novi should know its own relationship to its environment:

- current pose;
- current map;
- known home location where authorized;
- known operating areas;
- visited regions;
- localization confidence.

This is separate from the world map itself but references the same spatial infrastructure.

---

## 45. Temporal Self-Knowledge

Novi should understand temporal context:

- current time estimate;
- uptime;
- last restart;
- last upgrade;
- last calibration;
- recent experiences;
- time since last visit/event.

Clock uncertainty must be represented when relevant.

---

## 46. Self-Model Queries

The memory/API architecture should expose structured queries such as:

```text
get_identity()
get_hardware_state()
get_capabilities()
get_limitations()
get_health()
get_current_state()
get_software_versions()
get_model_versions()
get_self_knowledge()
get_self_history()
```

Responses must include provenance/authority where required.

---

## 47. Self-Model Audit

Important changes should be traceable:

```text
self-model field
   ↓
old value
   ↓
new value
   ↓
evidence/source
   ↓
policy
   ↓
software version
```

This enables investigation of changes in Novi's behavior and self-description.

---

## 48. Self-Model Evaluation

Evaluate whether Novi's self-model accurately reflects:

- installed hardware;
- current software;
- capabilities;
- limitations;
- health;
- current state;
- historical continuity;
- calibration;
- identity.

False self-capability is particularly dangerous for autonomous planning.

---

## 49. Self-Model Drift

Detect drift such as:

```text
self-model:
"camera works normally"

runtime:
frequent camera failures
```

This should trigger reevaluation rather than allowing outdated self-knowledge to persist indefinitely.

---

## 50. Safety Boundary

The self-model must never override safety state.

If Novi believes:

```text
"I can safely move"
```

but the safety subsystem reports:

```text
STOP
```

safety wins.

Self-knowledge is advisory for planning; safety authority is independent.

---

## 51. Security Boundary

The self-model must not reveal protected security information merely because the language model asks for it.

Examples:

- private keys;
- authentication secrets;
- security trust roots;
- protected credentials.

Self-awareness does not imply unrestricted introspection.

---

## 52. Privacy

The self-model may contain sensitive information about:

- home location;
- household members;
- routines;
- hardware identifiers;
- usage patterns.

Access must follow privacy and authorization policies.

---

## 53. Personality Integration

The self-model can provide factual context to personality/cognition:

```text
"I have visited this location before."
"My battery is low."
"My left camera is degraded."
"I learned this route last month."
```

Personality can determine how these facts are expressed, but not whether the underlying facts are true.

---

## 54. Continuous Evolution

Novi's evolution should operate across separate tracks:

```text
hardware evolution
software evolution
model evolution
knowledge evolution
experience evolution
behavior/personality evolution
```

Each track has different authority and evaluation requirements.

They must not be treated as one unrestricted self-modification process.

---

## 55. Evolution Gates

Significant self-model changes should pass through:

```text
new evidence
   ↓
validation
   ↓
classification
   ↓
policy
   ↓
optional evaluation
   ↓
projection
   ↓
audit
```

Critical identity/security/safety changes require stronger controls.

---

The architecture must handle:

- incorrect hardware inventory;
- stale capability information;
- failed sensor discovery;
- calibration drift;

- inconsistent software versions;
- hardware replacement;
- backup restoration;
- duplicated identity;
- fabricated autobiography;
- personality/self-model confusion;

- compromised self-state.

## 58. Architectural Invariants

1. Novi's self-model is grounded in authoritative system state and evidence.
2. The LLM cannot be the authoritative source of self-state.
3. Persistent identity is protected and explicitly governed.
4. Hardware identity and robot identity are distinct concepts.
5. Hardware replacement preserves historical provenance.
6. Capabilities and current capability availability are distinct.
7. Known limitations are first-class self-knowledge.
8. Current self-state is projected from authoritative runtime systems.
9. Historical experiences remain separate from current operational state.
10. Novi must be able to represent uncertainty and lack of knowledge about itself.
11. Novi must never fabricate missing autobiographical history.
12. Personality cannot rewrite factual self-state.
13. Self-improvement cannot silently modify security, safety or identity boundaries.
14. Duplicate active identities are prohibited unless explicitly modeled as separate instances.
15. Self-model reconstruction must work offline.
16. Self-model changes must be auditable.
17. Safety authority remains outside the self-model.
18. Sensitive self-information remains subject to privacy/security controls.

---

## 59. Final Principle

> **Novi should know what it is, what it can do, what it cannot do, what state it is in, and what it has experienced—but every important part of that knowledge must have a trustworthy source.**

The self-model provides continuity and embodied self-awareness for planning and interaction without turning Novi's language model into an unrestricted narrator of its own reality.
