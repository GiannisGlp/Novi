# 19 — Time Synchronization & Clock Semantics Architecture

**Status:** P0 normative architecture  
**Owner:** System Architecture  
**Scope:** All Novi software, sensors, actuators, events, memory, cognition, autonomy, simulation and deployment profiles.

## 1. Purpose

Novi must have one explicit answer to what a timestamp means.

Time is not merely metadata. It affects perception alignment, sensor fusion, localization, prediction, memory ordering, causality, action validity, safety, simulation, replay and recovery.

This document defines the system-wide time vocabulary and synchronization rules. It does not replace the semantic meaning of individual contracts in `16_CANONICAL_SYSTEM_CONTRACTS.md`.

## 2. Core principle

> **Never infer time semantics from a timestamp field alone. Every time-bearing value must identify which clock and which temporal meaning produced it.**

A timestamp without a defined clock domain is not sufficient evidence of temporal ordering.

## 3. Canonical clock domains

Novi distinguishes at least:

```text
WALL / SYSTEM TIME
    │
    ├── external-world correlation
    ├── logs
    └── human-visible timestamps

MONOTONIC / STEADY TIME
    │
    ├── durations
    ├── deadlines
    ├── timeouts
    └── scheduler measurements

ROS TIME
    │
    ├── ROS message/header semantics
    └── /clock-driven simulation when enabled

SIMULATION TIME
    │
    ├── simulated physics
    ├── simulated sensors
    └── deterministic replay

HARDWARE / SENSOR TIME
    │
    ├── camera
    ├── IMU
    ├── lidar
    ├── encoders
    └── audio devices
```

These clocks MUST NOT be silently treated as interchangeable.

## 4. Wall/system time

Wall/system time represents the host's externally meaningful civil/epoch clock.

Use it for:

- external timestamps;
- audit records where real-world date/time matters;
- correlation with external services;
- human-facing logs;
- legal/privacy lifecycle events where required.

Do not use wall time for measuring elapsed durations or scheduler deadlines because system-clock adjustments can make it jump.

## 5. Monotonic/steady time

Monotonic time is the preferred clock for:

- timeouts;
- watchdogs;
- retry intervals;
- latency measurements;
- scheduling deadlines;
- performance budgets;
- fault-detection windows.

Elapsed time MUST be calculated using a monotonic source whenever the platform provides one.

## 6. ROS time

ROS 2 time may represent system time or simulated time depending on the node's configuration.

Novi must explicitly configure and document `use_sim_time` for every ROS 2 component participating in simulation.

Isaac Sim documents the `/clock` topic and `use_sim_time` mechanism for synchronizing external ROS 2 nodes to simulation time. NVIDIA also documents that simulation time and wall time can progress at different rates and that ROS topic frequency observed by `ros2 topic hz` is measured against wall time. citeturn0search0turn0search2

## 7. Simulation time

Simulation time is the temporal domain of the simulated world.

It MUST be used consistently by simulated:

- physics;
- sensor generation;
- robot state;
- TF data;
- perception inputs;
- navigation inputs;
- world-model timestamps;
- deterministic replay where applicable.

Isaac Sim can publish simulation time over `/clock`, and ROS 2 nodes can subscribe to it through `use_sim_time`. citeturn0search0

## 8. Hardware and sensor time

Sensors may provide timestamps generated by:

- device clocks;
- embedded controllers;
- host drivers;
- hardware synchronization systems.

The source MUST be retained.

A driver MUST NOT silently replace a sensor timestamp with host receipt time without recording that transformation.

At minimum distinguish:

```text
sensor_capture_time
transport_time
host_receive_time
processing_time
```

## 9. Four-time model

For sensor/event pipelines, Novi should preserve these concepts where available:

```text
CAPTURE / OCCURRENCE TIME
        ↓
TRANSPORT / RECEIPT TIME
        ↓
PROCESSING TIME
        ↓
COMMIT / RECORD TIME
```

They answer different questions:

- When did the world event occur?
- When did Novi receive it?
- When did Novi process it?
- When did Novi make it durable?

## 10. Timestamp provenance

Every canonical time-bearing contract MUST be able to identify:

```text
clock_domain
clock_source
timestamp
precision
synchronization_status
uncertainty
```

Where a transformation occurs, the original timestamp MUST remain recoverable where semantically important.

## 11. Clock synchronization

Clock synchronization is an implementation concern of the deployment/runtime layer, but its semantic result is exposed to contracts.

The system must distinguish:

```text
SYNCHRONIZED
DEGRADED
UNSYNCHRONIZED
UNKNOWN
```

An unsynchronized clock MUST NOT silently be treated as synchronized.

## 12. Offset and uncertainty

A synchronized clock is not necessarily exact.

Novi should model:

```text
estimated_offset
estimated_uncertainty
last_sync_time
sync_source
sync_quality
```

Where timestamp alignment affects a consequential decision, uncertainty must be considered.

## 13. Temporal ordering

Novi MUST NOT infer global ordering from timestamps alone when clocks are not synchronized sufficiently for that conclusion.

Prefer explicit causal identifiers and event relationships where available:

```text
causation_id
correlation_id
sequence
source_id
```

This complements the canonical `EventEnvelope` semantics.

## 14. Sensor fusion

When combining measurements from different sensors, the fusion layer must account for:

- clock offsets;
- timestamp uncertainty;
- sensor latency;
- transport latency;
- processing latency;
- measurement age;
- dropped messages;
- out-of-order delivery.

A measurement must not be treated as contemporaneous merely because it arrived together.

## 15. Stale data

Every time-sensitive subsystem must define its maximum acceptable data age.

```text
measurement_age = now_in_compatible_clock_domain - measurement_time
```

If the clock relationship is unknown, the system must not pretend the age is known.

Possible states:

```text
FRESH
AGING
STALE
INVALID
UNKNOWN
```

## 16. Deadlines

Deadlines are duration/scheduling concepts and should use monotonic time.

A deadline MUST NOT depend on wall-clock arithmetic unless the requirement is explicitly tied to civil time.

## 17. Timeouts

Timeouts must be measured against monotonic/steady time.

A system clock adjustment must not accidentally extend or shorten a safety or runtime timeout.

## 18. Safety-critical timing

Safety-critical operations must have explicit timing budgets for:

```text
sensor acquisition
state estimation
policy evaluation
authorization
command generation
controller execution
actuator response
fault detection
safe-stop
```

The budget must include worst-case rather than average latency where safety depends on the bound.

## 19. Action validity windows

An action proposal or authorization may become invalid when its relevant state becomes too old.

Where required, contracts should include:

```text
created_at
valid_from
expires_at
state_version
policy_version
```

A stale authorization MUST NOT be treated as current merely because it was once valid.

## 20. Cognition temporal semantics

Cognition owns semantic temporal reasoning:

- before/after;
- duration;
- temporal intervals;
- recurrence;
- temporal causality;
- prediction horizons;
- historical validity.

System Architecture owns the clock semantics that make those timestamps interpretable.

## 21. Memory temporal semantics

Memory owns historical validity and experience timelines.

Memory MUST preserve enough temporal provenance to distinguish:

```text
WHEN THE EVENT OCCURRED
WHEN IT WAS OBSERVED
WHEN IT WAS RECORDED
WHEN IT BECAME KNOWN
WHEN IT CEASED TO BE VALID
```

A later record date does not automatically make a fact temporally newer.

## 22. Autonomy temporal semantics

Autonomy uses time for:

- goal deadlines;
- action validity;
- task scheduling;
- retry policy;
- behavior persistence;
- interruption;
- timeout handling.

Autonomy must not redefine system clock semantics.

## 23. Brain/runtime temporal semantics

Brain/runtime owns:

- scheduler clocks;
- execution deadlines;
- watchdog timing;
- runtime latency measurement;
- sensor-driver timing adapters;
- clock-domain conversion at runtime boundaries.

Brain must preserve semantic timestamps when forwarding data.

## 24. Simulation requirements

Simulation profiles MUST explicitly declare:

```text
clock_source
physics_step
render/update cadence
ROS /clock behavior
use_sim_time policy
reset behavior
replay behavior
real-time factor expectations
```

Isaac Sim distinguishes simulation time from wall time and documents Real-Time Factor as simulated elapsed time divided by real elapsed time. citeturn0search2turn0search5

Therefore a simulation running at 0.5 RTF is not equivalent to a physical robot operating at half its intended sensor/control frequency; these are different timing phenomena and must not be conflated.

## 25. Simulation reset

Simulation reset can cause temporal discontinuities.

All components participating in simulation MUST define behavior for:

```text
PAUSE
RESUME
RESET
FAST-FORWARD
SLOW-MOTION
REPLAY
```

A reset must not leave stale timestamps appearing newer than newly generated simulation data.

## 26. Replay

Deterministic replay should reproduce the relevant logical time domain rather than relying on wall time.

Replay metadata MUST identify:

- source recording;
- source clock domain;
- original time range;
- replay time mapping;
- speed factor;
- reset policy;
- software/model versions.

## 27. Recording

Recorded data should preserve original timestamps and the recording/receipt timestamps separately where useful.

The recorder MUST NOT normalize all time into one timestamp and thereby destroy provenance.

## 28. Cross-machine synchronization

Multi-machine synchronization is future architecture unless Stage 1 requires it.

When introduced, the system must define:

- synchronization protocol;
- master/reference strategy;
- maximum tolerated offset;
- maximum tolerated drift;
- uncertainty estimation;
- loss-of-sync behavior;
- recovery behavior;
- trust/security requirements.

## 29. Time authority

No single application component may invent a new authoritative clock for the system.

The hierarchy is:

```text
DEPLOYMENT CLOCK SOURCE
        ↓
RUNTIME CLOCK ADAPTER
        ↓
DOMAIN-SPECIFIC CLOCK VIEW
        ↓
CANONICAL CONTRACT TIMESTAMP
```

## 30. Contract integration

The canonical contracts should distinguish at minimum:

```text
occurred_at
recorded_at
processed_at
valid_from
valid_until
```

where applicable.

The exact fields belong to each contract's semantics; this document defines the system-wide vocabulary.

## 31. Failure behavior

If a required clock becomes unavailable or invalid:

```text
DETECT
 ↓
CLASSIFY
 ↓
DEGRADE / STOP / FAIL SAFE
 ↓
RECORD
 ↓
RECOVER / RESYNCHRONIZE
```

The correct behavior depends on the affected function.

A missing timestamp for a non-critical telemetry metric may be tolerated. A missing or untrusted timestamp required for safety-critical fusion may require the operation to stop.

## 32. Clock rollback

Wall-clock rollback MUST NOT break monotonic timeout or sequencing behavior.

Persisted event ordering must not depend solely on wall-clock timestamp ordering.

## 33. Leap seconds and civil time

External/civil timestamps must follow the selected platform standard consistently.

Internal elapsed-time calculations should remain based on monotonic time.

## 34. Precision

Precision must not be confused with accuracy.

A nanosecond-resolution timestamp from an unsynchronized clock is not necessarily more accurate than a microsecond-resolution synchronized timestamp.

## 35. Resource implications

Timestamp synchronization, high-frequency event logging and sensor fusion consume CPU, memory, storage and potentially network bandwidth.

Resource budgets defined by the system resource-governance architecture must include time-related telemetry where material.

## 36. Validation requirements

Before implementation approval, test:

### Clock

- monotonicity;
- wall-clock adjustment;
- clock drift;
- synchronization loss;
- synchronization recovery;
- timestamp precision;
- uncertainty propagation.

### Sensors

- capture vs receipt time;
- out-of-order delivery;
- dropped samples;
- delayed samples;
- sensor clock offset.

### Simulation

- `/clock` publication;
- `use_sim_time` behavior;
- pause/resume;
- reset;
- RTF variation;
- replay.

### Runtime

- timeout correctness;
- deadline correctness;
- watchdog behavior;
- stale-data rejection;
- action expiry.

### Recovery

- restart with persisted timestamps;
- crash during clock degradation;
- replay after recovery;
- schema/version compatibility.

## 37. Stage-1 implementation policy

For the first physical Novi implementation:

1. use the host/platform monotonic clock for durations, deadlines and watchdogs;
2. use system/epoch time for external-world and audit timestamps where required;
3. preserve ROS timestamps and clock semantics at ROS boundaries;
4. use a single explicitly configured simulation clock when running simulation;
5. record sensor timestamps without silently replacing them with receipt time;
6. defer multi-machine clock synchronization until a concrete multi-node requirement exists;
7. benchmark timestamping and synchronization overhead on the actual development platform before declaring timing budgets.

## 38. NVIDIA / Isaac validation baseline

NVIDIA's current Isaac Sim documentation explicitly supports ROS 2 clock publication/subscription and `use_sim_time`, and documents both simulation-time and system-time publication paths. citeturn0search0turn0search7

NVIDIA also documents that physics, timeline and run-loop rates can become unsynchronized if simulation-rate controls are changed independently. This reinforces the requirement that Novi's simulation profile treat timing as a coherent system rather than a collection of independent frequencies. citeturn0search2

These sources validate the integration model; Novi still requires its own benchmark and validation tests.

## 39. Definition of done

The time architecture is implementation-ready when:

- every clock domain is explicitly named;
- every time-bearing contract identifies its temporal semantics;
- sensor capture and receipt times can be distinguished;
- monotonic time is used for deadlines/timeouts;
- ROS simulation time behavior is explicit;
- simulation profiles define `/clock` and `use_sim_time` policy;
- timestamp uncertainty is represented where consequential;
- stale-data rules exist for time-sensitive subsystems;
- action validity windows are defined where required;
- replay/reset semantics are defined;
- clock failure behavior is tested;
- time-related resource budgets are measured;
- no subsystem silently invents a competing system clock.

## 40. Architectural invariant

> **Novi may have multiple clock domains, but it must never have ambiguous time semantics.**
